## Задача

Яндекс Недвижимость — маркетплейс для аренды и покупки жилья. В прошлом проекте была сделана базовая модель оценки рыночной стоимости квартиры. Задача текущего проекта заключается в улучшении основной метрики проекта, которая влияет на точность предсказаний стоимости недвижимости и, как следствие, на количество успешных сделок на маркетплейсе. Помимо этого процесс улучшения необходимо сделать воспроизводимым: все эксперименты логируются в MLflow, модели регистрируются в Model Registry, изменения фиксируются набором метрик и артефактов. С точки зрения машинного обучения это по-прежнему задача регрессии.

## Данные

Используется очищенный датасет `flats_buildings_clean` из предыдущей дисциплины. 

Состав данных:

- 123 525 строк;
- 15 входных признаков;
- целевая переменная: `price`;
- идентификаторы `id` и `building_id` не используются как признаки;
- булевы поля `is_apartment`, `studio`, `has_elevator` приводятся к `0/1`;
- категориальный признак `building_type_int` кодируется one-hot.

Для сравнения с baseline используется то же разбиение train/test: 80%/20%, `random_state=42`.

## Этап 1. Разворачивание MLflow и регистрация baseline

На этом этапе развворачиваем MLflow Tracking Server и MLflow Model Registry. Для хранения экспериментов использовалась база PostgreSQL; для артефактов использовалось S3-совместимое хранилище LocalStack в локальной Docker-эмуляции.

Сервисы поднимаются shell-скриптом mlflow_server/run_mlflow.sh, который запускает docker compose из vm-emulation (PostgreSQL в качестве backend store, S3-бакет mlflow-artifacts в качестве artifact store) и стартует MLflow Server в локальном виртуальном окружении.

Baseline-модель из предыдущего проекта зарегистрирована скриптом mlflow_server/register_baseline.py. В MLflow сохранены параметры модели, метрики на тестовой выборке, сигнатура, окружение, код и файлы модели. Модель зарегистрирована в Model Registry как real_estate_price_model, версия 1.

Контрольный результат: baseline воспроизвёл исходные метрики: MAE 2 003 737 ₽, RMSE 2 721 366 ₽, R² 0,774916.

## Этап 2. Проведение EDA

EDA содержится в ноутбуке model_improvement/model_improvement.ipynb.  Отдельный запуск в MLflow: `stage2_eda`.

В ноутбуке проверяем размер датасета и проверяем датасет на пропуски и дубли. 
Анализируем: 
- распределение цены в исходном и логарифмическом масштабн;
- распределение общей площади и количества комнат;
- корреляции признаков между собой и с целевой переменной;
- зависимость цены от площади, числа комнат, типа дома и географического положения.

Ключевые выводы:

1. В очищенной выборке 123525 строк, явных пропусков и дублей по id нет. Идентификаторы не подаются в модель.
2. Цена заметно скошена вправо: среднее около 12,48 млн.р., медиана составляет 11,0 млн р. Поэтому наряду с MAE важно смотреть RMSE, который сильнее штрафует крупные ошибки.
3. Сильнее всего с ценой линейно связаны следующие характеристики: 
- общая площаадь, total_area (r = 0,677)
- жил.площадь, living_area (r = 0,595)
- количество комнат, rooms (r = 0,511).
4. Тип дома и география лучше работают как категориальные и нелинейные зависимости. Это стало основанием для кодирования через one-hot encoder, биннинга координат и генерации взаимодействий.

Все графики, статистика и выводы оформлены в ноутбуке. В MLflow запуск stage2_eda содержит Jupyter Notebook, eda_conclusions.md, статистику и графики EDA. После выполнения всех этапов итоговый выполненный ноутбук дополнительно сохранён через запуск project_notebook_final.

## Этап 3. Генерация признаков и обучение новой версии модели

MLflow run: `stage3_feature_generation`.

Новые признаки собраны в единый `sklearn.Pipeline`:

1. Исходные числовые признаки сохраняются без изменений.
2. Для `total_area`, `living_area` и `kitchen_area` через `PolynomialFeatures(degree=2)` строятся квадраты и попарные взаимодействия площадей.
3. `latitude`, `longitude`, `build_year`, `floor` и `floors_total` через `KBinsDiscretizer(n_bins=5)` разбиваются на квантильные интервалы.
4. `building_type_int` кодируется через `OneHotEncoder`.
5. Для положительных числовых признаков отдельно запускается `autofeat.AutoFeatRegressor`, который подбирает преобразования вида `1/x`, `log(x)`, `sqrt(x)` и `x²`.
6. Ручная и автоматическая ветки объединяются через `FeatureUnion`, после чего данные передаются в Random Forest.

В MLflow сохранены Pipeline, сигнатура, параметры, скорость обучения и предсказания, список признаков, важность признаков и сама модель.

Метрики после генерации признаков:

- MAE = 2006002 руб.;
- RMSE = 2720082 руб.;
- R² = 0,775129.

Улучшение небольшое, но оно есть: RMSE снизился примерно на 0,047% относительно baseline. Этот результат тоже честно сохранён, без подгонки под ожидаемый вывод.

## Этап 4. Отбор признаков и обучение новой версии модели

MLflow run: `stage4_feature_selection`.

Чтобы последовательный отбор не был слишком дорогим, сначала по важности Random Forest отбираются 25 кандидатов из сгенерированного пространства признаков. Дальше на train-подвыборке используются два метода из `mlxtend`:

- **Forward Sequential Feature Selection** последовательно добавляет признаки;
- **Backward Sequential Feature Selection** последовательно удаляет признаки.

Оба метода работают с 2-fold CV и RMSE. Финальный список формируется из пересечения результатов и наиболее важных признаков их объединения. Test-выборка при отборе не используется.

В MLflow сохранены история CV, списки признаков, выбранные forward и backward методами, финальный список, график качества от числа признаков, важность признаков и новая версия модели.

Метрики после отбора:
- MAE = 2016018 руб.;
- RMSE = 2753192 руб.;
- R² = 0,769621.

На этом шаге качество немного ухудшилось относительно baseline и предыдущей версии. Это нормальный экспериментальный результат: отбор уменьшил избыточность, но часть полезных сочетаний признаков была потеряна. Сравнение оставлено в MLflow. 

## Этап 5. Подбор гиперпараметров и обучение финальной версии

MLflow runs: stage5_optuna_parent, stage5_random_search_parent, stage5_final_model и вложенные trial-запуски.

Для подбора гиперпараметров используются два метода:
- Optuna TPE (получилось где-то 20 попыток). Процесс оптимизации логируется через MLflowCallback, каждая попытка создаёт отдельный вложенный run.
- RandomizedSearchCV (15 итераций с 3-fold CV). Каждая комбинация параметров также сохраняется отдельным вложенным запуском.

Настраиваются n_estimators, max_depth, min_samples_leaf и max_features. Методы сравниваются по CV RMSE, а не по test, чтобы тестовая выборка оставалась только финальной проверкой.

Лучшим методом в локальном запуске оказался Optuna со следующими параметрами:
n_estimators=200
max_depth=20
min_samples_leaf=2
max_features=0.7

И вот какие метрики у нас получились на test:
MAE = 1 778 240 ₽;
RMSE = 2 477 366 ₽;
R² = 0,813469.

Относительно baseline RMSE улучшен на 8,97%! R² вырос на 0,03855. 
Финальная модель зарегистрирована в Model Registry как версия 4 и загружается через models:/real_estate_price_model/4.

## Окружение

Вместо ВМ курса локально поднимаем инфраструктуру через vm-emulation/docker-compose.yml:
mlflow-postgres — PostgreSQL 16, хранит эксперименты, метрики и Model Registry: 127.0.0.1:5433;
mlflow-localstack — S3-совместимое хранилище для моделей, графиков и ноутбуков: 127.0.0.1:4566;
mlflow-localstack-init при первом запуске создаёт бакет mlflow-artifacts;
mlflow-s3-restore заливает в бакет объекты из vm-emulation/s3-seed/ (LocalStack community держит S3 в памяти, поэтому восстановление делается при каждом старте);

MLflow Tracking Server запускается на хосте из виртуального окружения командой `bash mlflow_server/run_mlflow.sh` (скрипт сначала поднимает инфраструктуру через compose, затем стартует сервер и занимает терминал): 127.0.0.1:5000.

База postgres лежит в vm-emulation/volumes/pgdata/ и закоммичена в репозиторий: после клонирования `docker compose up` поднимает сервисы сразу с экспериментами и четырьмя версиями модели в Model Registry, а s3-restore наполняет бакет (85 объектов, ~608 МБ).

После запуска MLflow-сервера интерфейс доступен по адресу:

http://127.0.0.1:5000
Логины и ключи в local-emulation.env тестовые и работают только внутри локального Docker-окружения.

## Инструкция по запуску

Инфраструктура `vm-emulation/` есть только на ветке `main` (см. важное примечание выше); запуск оттуда поднимает MLflow сразу с историей проекта.

1. Создаём окружение и устанавливаем зависимости (mlflow входит в requirements.txt):

```shell
uv venv --python 3.11.15 .venv
uv pip install --python .venv/Scripts/python.exe -r requirements.txt
```

Перед запуском в папке проекта должны лежать:
- data/initial_data.csv — очищенный датасет из прошлого спринта;
- baseline/model.pkl — обученная baseline-модель;
- baseline/metrics.json — метрики baseline.

2. Поднимаем инфраструктуру и MLflow Server одной командой:

```shell
source .venv/Scripts/activate
bash mlflow_server/run_mlflow.sh
```
Скрипт запускает docker compose из vm-emulation (PostgreSQL, LocalStack и восстановление бакета S3 из s3-seed), затем стартует MLflow Server и занимает терминал. Интерфейс: http://127.0.0.1:5000.

3. В другом терминале регистрируем baseline:
```shell
python mlflow_server/register_baseline.py
```
Выполняем этапы 2–5 и логируем готовый ноутбук:
```shell
jupyter nbconvert --to notebook --execute --inplace model_improvement/model_improvement.ipynb --ExecutePreprocessor.timeout=7200
python model_improvement/log_notebook.py
```
Для быстрой технической проверки можно поставить FAST_RUN=true, но итоговый запуск выполняется с FAST_RUN=false.
